# Chapter 35 — 스트링·색상·선수 카드의 실제 이용 이벤트

페이지 조회만으로는 스트링 후보를 눌렀는지, 색을 바꾸었는지, 선수 카드에서
라켓을 찾아갔는지 구분할 수 없었다. 기존 이벤트 수집 API와 세션·캠페인
표시를 재사용해 사용자가 직접 한 세 가지 행동을 기록한다.

## 변경

- `string_pairing_click`: 라켓 상세와 진단 결과의 스트링 후보 링크에서
  발생한다. 출발 화면, 공개 라켓 slug·스트링 offer key와 후보 유형만 담는다.
- `customizer_change`: 사용자가 스트링·그립 색을 바꾸거나 선택을 초기화하면
  발생한다. 공개 라켓 slug, 사진/도식 구분, 행동과 변경 후 색상 ID를 담는다.
  사진과 도식은 기존 공통 컨트롤의 같은 핸들러를 쓴다.
- `player_racket_click`: 선수 카드에서 대응 리테일 라인 검색 링크를 누르면
  발생한다. 홈/선수 페이지와 공개 선수 ID만 담는다. 검색 URL의 쿼리는 담지 않는다.
- 링크의 작은 클라이언트 컴포넌트와 색상 조작 핸들러에만 계측을 붙였다.
  추천 계산·순위, 표시 문구·스타일, 원래 링크와 라디오의 동작은 유지한다.
  첫 렌더, 같은 색 재선택, 선택이 없는 초기화는 세지 않는다. 순수 reducer를
  다시 계산해도 이벤트는 발생하지 않으며, 추적 실패가 상태 변경·이동을 막지 않는다.
- 새 이벤트의 payload는 API에서 공개 식별자·허용 색상/선수·한정된 캠페인
  항목만 허용한다. 진단 ID, 답변·점수·추천 산식과 임의 필드는 거절한다.
  기존 QA `trafficType`과 캠페인은 유지한다. 새 이벤트의 현재 URL·referrer는
  `/results/<id>`를 `/results/[id]`로 축약하며 쿼리·fragment도 제거한다.
  기존 페이지 조회·진단 이벤트의 수집 계약은 변경하지 않는다.

## 데이터베이스 준비

`0007_product_interaction_events.sql`은 기존 `event_type` enum에 세 값을
`ADD VALUE IF NOT EXISTS`로 추가한다. 테이블·열·쿠키를 만들지 않는다.
API allowlist와 taxonomy, Drizzle schema를 동기화했다. 기존에 빠져 있던
`0006_snapshot.json`을 0005 스냅샷과 0006 변경 기준으로 복구하고,
오프라인 Drizzle generate로 0007 스냅샷과 journal을 만들었다.

이 작업에서는 운영 DB에 migration을 적용하지 않았다. 새 이벤트를 저장할
수 있도록 배포 전에 enum 추가를 적용해야 한다. 운영 적용 이력은 별도로 기록한다.

## 검증

로컬 `npm test` 319개, `npm run typecheck`, `npm run lint`, `npm run build`와
`git diff --check`를 통과했다. 새 회귀는 양쪽 스트링 출발 화면, 기본·키보드·
가운데 버튼 링크 활성화, 변경/동일값/초기화, 사진·도식 SSR와 reducer 재계산,
동기·비동기 추적 실패, URL 식별자 제거와 QA 보존, API payload 거절 및
enum/스냅샷 정합성을 확인한다. 기존 스폰서 테스트는 API 파일의 문자열 위치
검사 대신 공용 수집 schema가 이벤트를 실제로 허용하는지 검사하도록 바꿨다.

독립 검토에서 발견한 결과 URL 식별자 문제를 수정했고 재검토에서 P1/P2는
없었다. worktree의 외부 node_modules 심볼릭 링크 때문에 첫 로컬 빌드가
실패해 의존성 로컬 사본으로 재검증했다. 앱 설정이나 의존성 버전은 바꾸지 않았다.

## 해석과 남은 확인

이 이벤트는 클릭·선택 변경의 기록이다. 내용을 읽었다는 증거, 주문·구매,
고유 고객 수나 제품의 효용 검증으로 해석하지 않는다. 추적 차단·네트워크 실패는
누락을 만들 수 있고 QA/내부 트래픽은 별도로 구분해야 한다.

실제 브라우저에서의 hydration·키보드 조작과 운영 DB 저장 성공은 CI/프리뷰,
마이그레이션 적용, 배포 후 검증 단계에서 확인한다. SSR와 순수 reducer 검사는
실제 브라우저에서의 StrictMode 상호작용 검증을 대신하지 않는다.
